Getting started

It is a single program: put it on your own computer and on each host you want to reach. One line does that, checking the file's SHA-256 against the list on this site:

curl -fsSL https://sshremote.dev/install.sh | sh   # macOS and Linux
irm https://sshremote.dev/install.ps1 | iex        # Windows, in PowerShell
brew install --cask sshremote-dev/tap/sshremote    # macOS with Homebrew
brew install sshremote-dev/tap/sshremote           # Linux with Homebrew

It goes to ~/.local/bin/sshremote on Linux, to Applications on a Mac (its program is /Applications/SSH Remote.app/Contents/MacOS/sshremote, for SSH and the command line), and on Windows to %LOCALAPPDATA%\Programs\SSH Remote, with a Start menu entry and the folder on PATH. There are builds for Windows and Linux on x86_64 and Arm and one Mac app for Apple silicon and Intel; the files themselves are on GitHub Releases (see the download section). For many Windows computers at once there is an MSI, for all users, in Program Files: msiexec /i sshremote-windows-x86_64.msi /qn SERVICE=1 TEAM_URL=https://team.example.com TEAM_TOKEN=T installs it silently (Group Policy, Intune), with remote access as a service and the computer in a team if those are given, and AUTOUPDATE=0 keeps the service from updating itself; an upgrade needs no restart, and msiexec /x takes it away with the service. To remove it otherwise: sshremote remote-access uninstall if you installed the service, then delete the program (on Windows also its Start menu entry and the PATH entry), and its settings folder if you like (~/.config/sshremote; %APPDATA%\sshremote on Windows).

sshremote

With no arguments it opens the home window. On the left is this computer as others reach it: its remote access ID, IP addresses and SSH address, each copied with a click, and the Remote access by ID switch. On the right is one address field for user@host, an alias, an IP or an ID; it says what it reads and opens a terminal, the screen or the files there. Under it are your computers: this computer, favorites, the last opened and the aliases of ~/.ssh/config, each with a sheet for its name, key, saved password and SSH tunnels. The gear opens the settings. What you open goes into the workspace as tabs and panes; each pane switches between terminal, screen and files from its mode menu.

Connecting by SSH

The usual way: the viewer runs ssh -T HOST sshremote --agent, so your keys, agent, jump hosts and ~/.ssh/config work unchanged and nothing else needs to be reachable.

sshremote --gui user@host                 # the workspace
sshremote --gui user@host --open files    # straight to the files
sshremote terminal user@host --split db   # terminal panes, split
sshremote user@host                       # the screen in this terminal (sixel or kitty images)
sshremote user@host --preset 0            # 0 black and white 30 fps .. 4 true colour 60 fps

A lost connection is tried again in the same mode, keeping the shells; after 30 seconds the pane offers Reconnect or Close.

Windows hosts. The agent starts a helper in the logged-on user's session. To see the sign-in screen and send Ctrl+Alt+Del, add the service once (elevated, or with Start with the computer in the remote access settings): sshremote --install-service.
Mac hosts. macOS lets a program record its screen and control it only once its person allows it, in System Settings > Privacy & Security: Screen & System Audio Recording and Accessibility for SSH Remote. macOS asks the first time, and the viewer is told which one is missing (meanwhile the screen is shown without control, or terminals and files work alone). By ID the agent runs from the app, so the app's permissions count; over SSH it runs under the SSH server, whose permissions count instead (sshd-keygen-wrapper in those lists). The app is signed with one certificate for every version, so what was allowed stays allowed after updates. Start with the computer also asks once for an administrator's password, to reach the Mac at its login window: there the screen, the pointer and the keys work (to sign in), while terminals, files, programs and chat wait until someone signs in. That works from the login window the Mac starts up to, too; only FileVault's unlock, before macOS starts, cannot be reached. From a computer that is not a Mac, Ctrl and the command key trade places there, so Ctrl+C and Ctrl+V copy and paste on the Mac as here (the Win key is the Mac's Ctrl); the keys menu has the Mac's own shortcuts (lock screen, Spotlight, Force Quit and more) and a box to send the keys as they are. The Mac's resolution is set from the Display menu by the sizes System Settings lists.

Connecting by ID through the relay

For a PC without SSH or a fixed address, for example a laptop on Wi-Fi, the way RustDesk works. The PC keeps a lasting 9-digit ID, the same across restarts, and a password its owner sets or generates. A viewer connects with both through the relay.

On the PC to reach

Turn on Remote access by ID on the left of the home window. It shows the ID and the password (copy, show and a new one), a line telling the state and who is connected, each with Disconnect. Remote access settings hold Start with the computer, which installs the Windows service or a systemd user unit (on Windows the service also covers the sign-in and lock screens), your own password, the relay server and a new ID.

The same sheet sets who comes in and what they may do: ask the person at this computer first (a viewer with the right password waits for a click; nobody answering within a minute turns them away), the rights viewers have (keyboard and mouse, clipboard, files, sound and calls, terminals, restart and lock, tunnels; changed for one session in the window shown on this computer, which also ends it), two-step sign-in with an authenticator app's code, being found on this network, and letting viewers on it come straight in (TCP 7073) rather than through the relay. Anyone on a network can answer for an ID, so a viewer believes an address found there only until one turns down a password: it then asks the relay, which reaches the computer itself, and from then on goes straight only to addresses where the password got in before.

Straight through the routers. Once the password is right, the two computers look for a path between them that skips the relay (NAT hole punching, as RustDesk does): each asks the relay over UDP which address its router shows, they swap those and their own addresses (IPv6 ones too, which no router changes) inside the sealed connection and try each other's; over IPv6 the same tries open the routers' firewalls. When one works the session moves onto it without a pause, and the relay carries nothing more; a lightning sign in the screen's toolbar says so, a globe while it runs through the relay. When no path is found (routers that change the port for every destination on both sides, or networks without UDP) the session simply stays on the relay. The computer turns this off with Let viewers by ID go straight through the routers in its remote access settings, the viewer under Settings → Connections.

Passwords. Viewers give the lasting password, a one-time password shown beside it (like k7qp-2mz9), or either, as the settings say. A one-time password works for one connection and the minute after it (so a dropped viewer comes back in); then a new one takes its place, and whoever was helped once cannot come back later with it. Who is connected now, and how (through the relay or straight), shows in the window and the icon's menu, each with a way to end it.

Asking without a password. Where the person at the computer turned on Let people without the password ask to come in, someone with only its ID leaves the password empty (in the app, the web page or --password ""). The person there is asked, and both screens show the same six-digit code, made from the key exchange itself: someone in the middle would show another, so they compare it before clicking Let them in. One request at a time.

Only from some addresses. In Who comes in, Only from these addresses takes addresses and ranges (203.0.113.7 192.168.1.0/24 2001:db8::/32): a viewer from anywhere else is turned away before the password is even checked, and told why. Through the relay it is the address the relay sees the viewer from (a relay older than 1.2 does not say, and then nobody comes in past a list); through the web page, the address of its server. sshremote remote-access from … | anywhere sets it from a terminal.

Trusted devices. With two-step sign-in on, the viewer that gives the code can tick Do not ask for the code on this computer for 90 days: the computer gives it a token, kept in that viewer's system password store, and from then on its password alone lets it in (a request without a password still asks the person there). The computer keeps only the token's checksum, tied to its two-step secret: setting two-step sign-in up again, or turning it off, trusts no device any more. Its remote access settings say how many devices are trusted and Forget them, which also ends the sessions they are in; sshremote remote-access trusted lists them and trusted forget does the same.

Who came in. Lately under the ID lists who came in, how (the lasting or a one-time password, by asking, from a trusted device) and for how long, and who was turned away and why (a wrong password or code, an address not on the list); sshremote remote-access log prints the same.

Sessions left idle, recorded. End a session left idle ends one whose viewer has sent no keys, clicks or wheel for the minutes chosen, and tells the viewer why. Record each session by ID keeps every one as an MP4 file on this computer, at the screen's size (up to 1920×1200), and tells the viewer it is recorded. The files go in Videos (or Downloads), in a folder "SSH Remote sessions" that only its owner opens; on Windows, where the service runs the sessions, in ProgramData\SSH Remote\Session recordings, which only administrators open. A file is written in pieces of two seconds, so one cut off (the computer turned off) plays up to its end; recording stops while less than 1 GB is free on the disk.

Through a proxy. Where nothing goes out but through a proxy, Settings → Connections → Proxy takes it as socks5://host:1080 or http://name:password@host:8080 (an HTTP proxy that lets CONNECT through to the relay's port, 7071, or 80; one that allows only 443 does not reach it, a SOCKS proxy does). The password is shown as *** there and kept out of backups made without a passphrase. The relay, updates and extensions are then reached through it, by the viewer and by remote access on this computer, and no straight path is looked for around it; sshremote remote-access proxy URL | off sets it from a terminal.

The icon. Once the service is installed, an icon starts with each sign-in: in the notification area on Windows, in the top bar on Linux (GNOME's AppIndicator extension, on in Ubuntu). A click opens SSH Remote; its menu turns remote access on and off, copies the ID, sets who comes in, brings up the window of whoever is connected and starts, stops or removes the service. That window on the computer being viewed stays in the taskbar while someone is connected, so the connection can always be ended there.

Transfers that go on. Files sent or fetched when the connection breaks are not lost: what arrived of them is kept on both sides, and once the connection is made again (the pane does it by itself) each goes on from where it stopped, a folder's files that had arrived left out. The bytes just before that point are compared first, so a file changed meanwhile comes whole again instead.

Mouse for games. In a screen's options, Mouse for games holds the pointer in the window and sends how the mouse moves rather than where it is, for games that turn with the mouse; Ctrl+Alt (pressed and let go with no other key) lets it go, a click on the picture holds it again. It needs the whole screen shared, not one window.

On the viewer, the screen's toolbar also locks or restarts the computer, keeps its own keyboard and mouse out and hides its screen from whoever sits there (Windows; Ctrl+P there takes them back), locks it on leaving, calls the person there, and records the screen to an MP4 file.

From any browser, without installing anything: open web.sshremote.dev (Open in browser at the top of every page here), type the ID and its password, and the screen opens in the page with keyboard and mouse, the files beside it.

On the viewer

Type the ID (digits only) in the address field, then the password, and choose Screen sharing or Files.

From the command line

sshremote remote-access on           # also: status, off, run
sshremote remote-access password     # a new one; password NEW sets yours
sshremote remote-access id           # a new ID
sshremote remote-access install      # start with the computer; uninstall
sshremote remote-access relay HOST   # use another relay
sshremote remote-access ask on       # the person here lets each viewer in
sshremote remote-access allow keyboard files sound   # what viewers may use
sshremote remote-access straight off # always through the relay
sshremote remote-access passwords both  # lasting, one-time, or both
sshremote remote-access viewers      # who is connected; end N ends one
sshremote remote-access log          # who came in and who was turned away
sshremote remote-access idle 30      # end sessions idle for 30 minutes; idle off
sshremote remote-access trusted      # devices let in without the code; trusted forget
sshremote remote-access record on    # record each session by ID
sshremote remote-access proxy socks5://HOST:1080   # reach the relay through a proxy; proxy off
sshremote remote-access service stop # the service, kept installed
sshremote sshremote://ID --password P [--code C]
sshremote find                       # computers nearby with remote access on
sshremote wake 3c:52:82:1a:2b:3c     # Wake-on-LAN

Your own relay

The relay is a small program of its own, sshremote-relay, listening on TCP 7071, and on UDP 7071 to tell computers where it sees them from (for straight paths; open both in a firewall). To run your own and keep its IDs in a file:

sshremote-relay --listen 0.0.0.0:7071 --store /var/lib/sshremote/ids.json

Working in panes

Web apps (the Web apps extension). Type an https:// address on the home or in Quick open (+) and choose Open in a pane; + beside it keeps it in the list. Installed extensions add theirs under Tools (the Web apps extension: Google Translate, Papago, DeepL, Claude, ChatGPT, Gemini, Gmail, Calendar, Keep, Notion). Each runs as a page of Chrome, Edge or Chromium with no window of its own, laid out at the pane's size beside your terminals and screens, with back, forward and reload; its site keeps its sign-ins in a profile of its own. Ctrl+V pastes this computer's clipboard there and Ctrl+C copies back.

Files and screenshots into a terminal. Drop files on a terminal, or paste them (or a screenshot) with Ctrl+V: they are copied into a folder of their own where its shell runs and their paths are typed at the prompt, the way an AI agent like Claude Code takes a dropped file or picture. Progress shows in the pane's corner; what is a day old is cleared from that folder as new files come.

Screenshots between computers. In a screen session a picture copied on the other computer comes onto this one's clipboard (up to 4 MB), and Ctrl+V on its screen with a picture on this clipboard pastes it there; files copied here paste there as files too. The web page does the same in Chrome, Edge, Firefox and Safari.

Projects. The box beside + keeps the open tabs under a name: each pane's computer and what it shows, and how the panes divide each tab, never a password. Open them again from there or from the home; the tabs open when the app closes are kept as Last session, which Settings, Connections can open with the app.

Programs in a pane (the Programs extension), opened three ways: Search finds a computer's installed programs by name as the Start menu's search does, Command runs a command line as Run does (a folder, a file or an address opens with its program), and File opens a file or a folder picked from its folders. What it starts opens in a pane, showing that program alone and taking its clicks and keys, as RemoteApp does. Home's Tools and Quick open, also when splitting a pane, open this computer's programs; on Windows, in X11 sessions, and under Wayland on GNOME (with its sshremote helper), KDE Plasma, Sway and Hyprland the program's own window is held in the pane, moved and sized with it and closed with it, and shown only once it is in place. They are opened there only, in the new-open view: a screen's toolbar and the web page offer none. Without the extension the Tools are not there.

Resolution of the host's screen. The Display menu of a screen (the quality menu on the web page) lists the resolutions the host's screen can take, as RustDesk's does: picking one sets the screen itself to it, as its display settings would, and it is set back when the connection ends (Back to its own does it sooner). This is not the picture's size: Picture size in the quality and the zoom below 100% only send a smaller picture, the screen staying as it is. It works on Windows, X11 desktops, GNOME, KDE Plasma (with kscreen-doctor), Sway, Hyprland and COSMIC; a virtual screen there (one without modes of its own) takes the common sizes. Hyprland on a virtual machine's graphics is left out: it cannot make a screen larger again once it made it smaller.

Monitors. A computer with several monitors lists them in the monitor menu, each shown when picked; on KDE Plasma and other desktops that share their screen through their portal, every monitor is shared at once (chosen in the dialog the first time) and switching between them asks nothing more.

Cameras. A computer's cameras are listed after its monitors (the monitor menu); pick one to look at it, as RustDesk's view camera. Someone who comes by the ID sees them only when that computer's remote access settings allow it, and the person there is told each time.

Updates. The app looks once a day for a newer version, its list signed by sshremote.dev and checked before anything is used; Update puts it in place of the one running and Start again starts it. sshremote update --check only looks; sshremote update puts it in place. Settings turns the daily look off.

Markdown view. A terminal's output read as Markdown can be copied whole or downloaded as a .md or .txt file, and each code block copied or saved as a file of its language.

Using extensions

Browse the extension list, or open Settings → Extensions in the app (tabs Installed, Browse and Manage). From the command line:

sshremote ext available          # what the signed registry offers
sshremote ext install ID         # install or update
sshremote ext install FILE.sshx  # from a file

The kinds: style packs (pictures and animations behind the terminals), scripts (WebAssembly commands on the selected text, with no file or network access), programs (new sshremote commands such as web and mcp) and resident extensions (status bar items, panels, palette commands, keys and settings). Each request is checked against the permissions in the manifest, shown on the Extensions page.

Building extensions

An extension is a folder with an extension.json manifest. Programs speak JSON-RPC 2.0 over stdin and stdout, one message per line, so any language works. Start from the Rust template, which has a status bar item, a command with a key, a panel, a setting and a form:

sshremote ext new my-extension
sshremote ext dev my-extension

ext dev builds, installs and reloads it in the open app every time a file changes. To share one, pack it with sshremote ext pack DIR OUT.sshx. The manifest, the permissions and the full protocol are in docs/extensions.md.

MCP for AI agents

sshremote mcp HOST (or sshremote mcp --here for this computer) is an MCP server that reads the window in front as text from the accessibility tree and acts on its controls, taking screenshots only when needed. In your agent's MCP configuration:

{"mcpServers": {"remote-pc": {"command": "sshremote", "args": ["mcp", "user@host"]}}}

Security and FAQ

Is anything sent to a server of yours?

Not over SSH: the connection is your own SSH session from end to end. Only the ID and password mode uses the relay.

What can the relay see?

Nothing it could read. The viewer and host agree on a key from the password with SPAKE2, so the password never crosses the network, and seal every message with ChaCha20-Poly1305. The relay only pairs the two and copies sealed bytes.

Can someone take over my ID or guess the password?

An ID is held at the relay by a secret token only your computer has. Each wrong password is answered more slowly than the last; twenty in a row from one address (or IPv6 network) stop it being checked from there for a day, and a hundred from many places stop the checking from everywhere you have not come in from lately, so a guesser cannot lock you out. The relay limits the attempts from each address, and a straight path's every packet is checked, so nobody else can end or turn a session.

Are passwords stored?

Not unless you choose to. Passwords you choose to save go to the system's password store, and backups of ~/.ssh are encrypted under a passphrase.

How are extensions checked?

The registry's index is signed, each package is checked by its SHA-256, and native extensions are packed per platform. At run time every request is held to the manifest's permissions.

Which systems work?

Hosts: Windows; GNOME on Wayland; X11 desktops (Xfce, MATE, LXQt, Cinnamon, i3, KDE or GNOME on Xorg), with no dialog; Hyprland, Sway and other wlroots-based desktops, with no dialog; other Wayland desktops through their screen-sharing portal (KDE Plasma, COSMIC: allowed once at the screen). Where the screen cannot be shared, the terminal and files still work. Viewers: the native window on Windows and Linux, or a terminal that shows pictures: sixel (Windows Terminal, foot, VTE) or kitty images in true colour (kitty, Ghostty, WezTerm).
